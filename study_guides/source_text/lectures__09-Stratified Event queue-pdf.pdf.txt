Simulation Behavior vs Hardware Behavior
• Need to make sure simulation matches hardware
• Verilog defines how ordering of statements is interpreted by both
  simulator and synthesis tools
• Simulation matches hardware if code is well-written
  • Can have some differences with “bad” code
   • Simulator is sequential
   • Hardware is parallel                                “Making it work” in simulation does
   • Race condition can occur                            not mean it will work after synthesis

• Standard guarantees some scheduling order
  • Statements in the same begin-end block are “executed” in the order they appear
  • Statements in different begin-end block in same simulation time have no order
    guarantee

Verilog Stratified Event Queue
• Impose a defined order on how events get processed in the same
  simulation step
• Terminologies:
 • Processes:
   • Objects that can be evaluated
   • Includes primitives, modules, initial and always blocks, continuous assignments, tasks,
     procedural assignments.
 • Update event
   • Change in the value of a net or register (LHS assignment)
 • Evaluation event
   • Computing the RHS of a statement
 • Scheduling an event
   • Putting an event on the event queue
Verilog Stratified Event Queue
• Terminologies:
  • Simulation time:
   • Time value used by simulator to model actual time
  • Simulation cycle
   • Complete processing of all current active events
  • Can be multiple simulation cycles per simulation time
  • Explicit zero delay (#0)
   • Forces process to be an inactive event instead of active
   • Incorrectly used to avoid race conditions    Read more in the Cummings SNUG paper
   • #0 does not synthesize!
   • Don’t use it
Verilog Stratified Event Queue
• Events can go on one of 5 queues
• Region 1: Active Events
  • Most events except those explicitly in other regions
  • Includes $display system tasks
• Region 2: Inactive Events
  • Processed after all active events
  • #0 delay events (bad!)
• Region 3: Non-blocking Assign Update Events
  • Evaluation previously performed
  • Update is after all active and inactive events complete
• Region 4: Monitor Events
  • Caused by $monitor and $strobe system tasks
• Region 5: Future Events
  • Occurs at some future simulation time
  • Includes future events of other regions
  • Other regions only contain events for CURRENT simulation time
Simulation Model
Let T be current simulation time
while (there are events) {
    if (no active events) {
          if (inactive events) activate all inactive events
          else if (n.b. update events) activate all n.b. update events
          else if (monitor events) activate all monitor events
          else {    advance T to the next event time
                    activate all future events for time T }
    }
    E = pull from active event queue
    if (E is an update event) {
          update the modified object
          add evaluation events for sensitive processes to the event queue
    } else { // evaluation event
          evaluate the process
          add update event(s) to the event queue
    }
}
