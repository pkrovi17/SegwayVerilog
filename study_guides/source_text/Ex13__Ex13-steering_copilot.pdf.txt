What Is a FIFO?
A FIFO (first in, first out) is a buffer that stores data and returns it in the same order it arrived. It sits
between a producer that writes data and a consumer that reads it, letting the two run at different rates
for short periods without losing data. FIFOs appear throughout digital systems: network interfaces, video
pipelines, and anywhere one block produces data in bursts that another block consumes steadily.
    A synchronous FIFO uses a single clock for both reading and writing. It is usually built from a small
memory array used as a circular buffer, with a write pointer marking where the next entry goes and a
read pointer marking the oldest entry. Status flags tell the producer when the FIFO is full (stop writing)
and the consumer when it is empty (nothing to read). The interesting design work is in the boundary
cases: what should happen when someone writes to a full FIFO, reads from an empty one, or does both
at the same time?

The Specification
 module sync_fifo #(
    parameter int WIDTH = 8,
    parameter int DEPTH = 16   // always a power of 2, >= 2
 )(
    input logic              clk,
    input logic              rst_n,     // asynchronous, active-low
    input logic              wr_en,
    input logic [WIDTH-1:0] wr_data,
    input logic              rd_en,
    output logic [WIDTH-1:0] rd_data,
    output logic             full,
    output logic             empty,
    output logic [?:0]       count,     // entries stored; you choose the width
    output logic             overflow, // 1-cycle pulse
    output logic             underflow // 1-cycle pulse
 );

  1. Reset: empties the FIFO. It will also set count = 0, rd_data = 0, overflow = underflow = 0.
  2. Write: on a rising edge, if wr_en and not full, store wr_data.
  3. Read: on a rising edge, if rd_en and not empty, the oldest entry appears on rd_data (registered,
     so one cycle after rd_en). rd_data holds its value when no read occurs.
  4. Write while full (no read): ignored; overflow pulses for one cycle.
  5. Read while empty: ignored; underflow pulses for one cycle.
  6. Read + write while full: both succeed; count stays DEPTH; no overflow.
  7. Read + write while empty: only the write succeeds; underflow pulses; count becomes 1.
  8. count represents the number of valid entries stored and must be wide enough to represent 0 through
     DEPTH inclusive.
  9. full and empty are combinational signals from current state.

  • Experiment B: alternatives. At one point in the design, press Ctrl+Enter [T5] and look at at
    least three suggestions. Were all alternatives correct?
Finish the design. You’ve learned the coding style expectations in this class. Did the generated code
follow it? Can you wrangle it to follow better style? Steering tip for the coding style: a comment that
names a register, its reset value, and its update condition (for example, // Write pointer: reset to
0, increments on a successful write) is a strong [T3] prompt. Without it, Copilot tends to put
every register in one large block. A few quick checks you should do on the design before we move on to
the testbench: do we have one always_ff per register group (different reset or enable ⇒ different block),
nonblocking assignments, async active-low reset, count wide enough for DEPTH, rules 6 and 7 correct,
single-cycle pulses.

Round 3: Testbench                                                                    [T6] [T7] [T8] [T9]
Copy tb_skeleton.sv and rename it tb_sync_fifo.sv. The clock, DUT instance, checker, coverage,

  • Experiment C: open-tab context [T7]. With sync_fifo.sv open in another tab, start typing

  • Naming [T8]: write at least one directed test as a task with a descriptive name and let Copilot fill

  • Example, then pattern [T9]: write one directed test by hand, then let Copilot generate the next
    ones.
  • Partial accept [T6]: use word-by-word accept at least once on a suggestion that was only partly

Run the testbench on your design. It must print RESULT: PASS. The summary fails if your directed tests
never reach full, overflow, underflow, or either read + write case. If you have a lot of time remaining, try
adding 1,000+ cycles of random traffic.
