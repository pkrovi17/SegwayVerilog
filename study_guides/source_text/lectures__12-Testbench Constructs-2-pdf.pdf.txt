File I/O
• We may not want to hard-code all information in the testbench
  • Files hold the data, and the testbench provides the structure
• Help automate testing
  • One file with the input stimulus
  • One file with the expected outputs
  • The testbench compares the DUT's outputs against the expected values
• Can have software (Python, MatLab, System C) generate data
  • Create the inputs for testing
  • Create “correct” output values for testing
  • Can use files to “connect” hardware/software system
• Can write results out too: logs, summaries, data for post-processing
• Initialize memories (ROM, flash) from files

• Opening / Closing files:
  • $fopen opens a file and returns an integer descriptor
    integer fd = $fopen("filename");
    integer fd = $fopen("filename", "r");

    • If file cannot be open, returns a 0
    • Can output to more than one file simultaneously by writing to the OR ( | ) of the relevant file descriptors
      • Easier to have “summary” and “detailed” results
  • $fclose closes the file
    $fclose(fd);

• Writing to files:
  • Take the file descriptor as the first argument, then a formatted string
    • $fmonitor()
    • $fdisplay()                  $fdisplay(fd, "out=%b in=%b", out, in);
    • $fstrobe()
    • $fwrite()

Functions
• Declared and referenced within a module
  • Called from expressions (RHS)
  • Can call other functions
• Synthesizable functions implement combinational logic
  • No timing controls (#, @, wait) and no task calls
  • Must execute in zero simulation time
  • Use blocking assignments
• Arguments and return value
  • Returns value is assigned to the function name (unless a void function)
  • Must have at least one input (optional in SystemVerilog)
  • Can have output arguments (new with System Verilog)
• Uses
  • DUT code: conversions and calculations (e.g., saturation)
  • Testbench: self-checking routines that return pass/fail (Tasks are often a better fit)

module ALU(RF,mem,instr,cin,dst,src0sel,src1sel);
  input [15:0] RF,mem,instr;
  input cin,src0sel,src1sel;
  output [15:0] dst;

  wire [15:0] src0,src1;                                       Function performs a saturation, limiting
                                            function call      the output to a signed number in range:
  //////// muxing for Src0 & Src1 busses ////                  [-256,255]
  assign src0 = src0sel ? RF : ceiling9(mem);
  assign src1 = src1sel ? instr : RF;
                                                               Synthesizes no problem
  //////// implement adder /////////
  assign dst = src1 + src0 + cin;

  function [15:0] ceiling9(input [15:0] in_word);
    ceiling9 = (in_word[15] && ~&in_word[14:8]) ? 16'hFF00 :
               (~in_word[15] && |in_word[14:8]) ? 16'h00FF :
                in_word;
  endfunction
endmodule

Tasks
• More general than functions

 Functions:                                        Tasks:

 Can call other functions, but not tasks           Can call other tasks and functions

 Zero simulation time: no #, @, or wait            May consume time: #, @, wait allowed

 Return a value (or void); used in expressions     No return value; called as a statement

 At least one input (Verilog); outputs added in
                                                   Zero or more input, output, or inout arguments
 SystemVerilog


  Tasks can modify & monitor global signals too. Not the best style, but can be quite convenient.
Why use tasks?
• Tasks provide the ability to
  • Execute common procedures from multiple places
  • Divide large procedures into smaller ones
  • Declare local variables
• Very handy for testbenches
  • Break common testing routines into tasks
    • Initialization tasks
    • Stimulus generation tasks
    • Self Checking tasks
  • Top level test then becomes mainly calls to tasks.

Packages in System Verilog
• Old school Verilog did not have a shared declaration space. Each module had to
  contain all declarations used within that module, including tasks, functions,
  localparams, and typedefs.
• System Verilog added user defined packages to provide a declaration space that
  can be shared by any module.

• Example package:

           package alu_types;
             localparam delay = 1;

             typedef enum logic [3:0] {ADD, AND, XOR, SHFT_L, SHFT_R} op_t;
           endpackage
Packages in System Verilog
                             • Remember this rather clumsy example
                               use of typedef from before?
                             • We had to create an internal version
                               (op_i) of the opcode and then type cast
                               the 3-bit port variable to be of op_t.
                             • This was because the port could not be
                               of type op_t because it could not be
                               defined outside the scope of the
                               module itself
                             • Packages let us do that.
Packages in System Verilog
• With use of package the port op can be defined as op_t thus no need for the
  intermediate signal and cast.
  package alu_types;
    localparam delay = 1;

    typedef enum logic [2:0] {ADD, AND, XOR, SHFT_L, SHFT_R} op_t;
  endpackage
Use of packages for testbench tasks
                           • Can put localparams and tasks/functions
                             together in same file.


                           • All tasks/functions declared in a package
                             have to be automatic if any of their
                             arguments are ref


                           • Unfortunately, you cannot reference
                             global signals from the testbench level of
                             hierarchy, so all signals to monitor/control
                             should be passed as type ref
Use of packages for testbench tasks

                             • Any signal a task monitors has to be
                               passed as type ref, and therefore
                               cannot be declared as wire (use logic)


                             • Calls to tasks will have to pass
                               references to any signals the task drives
                               or monitors. These tasks cannot
                               “monitor” global testbench signals.
