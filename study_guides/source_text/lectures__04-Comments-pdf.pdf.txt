Comments
• Comments are VERY important!
 • In industry, others will have to read your code
 • Some poor soul (perhaps you 4 years later) are going to have to reference your
   code when a customer discovers a bug

• The best comments document why you are doing what you are doing
 • Motivation, thought process

• Good to have module-level or block comments
 • Avoids having to read detailed Verilog code if just browsing through
Comments Example

• Naming conventions:
 • Use mixed case and/or _ to delimit descriptive names
     assign parityErr = ^serial_reg;
     nxtState = returnRegister;
 • Consistent suffix for signals of same type
   • Use _n for active low
     rst_n = 1’b0; // assert reset
Implicit net declarations
• Always declare all signals before use
• When signal is used but not declared, it will be implied
  • Default to single bit wire…
  module majority(output out, input a, b, c);
    assign part1 = a & b;
    assign part2 = a & c;
    assign part3 = b & c;
    assign out = part1 | part2 | part3;
  endmodule

  module fulladder(output Sum, Cout, input A, B, Cin);
    assign {Cout, Sum} = A + B + cin;
  endmodule


• Disable by using `default_nettype none directive

Can Coding Style Affect Synthesis?
• HDLs abstract hardware design → do we have to consider the hardware?
   • Good hardware design requires ability to analyze a problem to find simplifications
   • Multiple variables: throughput, area, latency, power
   • Finding an optimal hardware implementation is a computationally complex
     problem → synthesis tool need guidance on where to start
